# forward_traffic_ml 技術仕様

## 1. 目的

`forward_traffic_ml` は、車両を通常の順方向に発生・移動させ、その結果として得られる観測点通過台数を実測の断面交通量に近づけるための実験プロジェクトです。

`inverse_traffic_simulator` では、観測点の不足通過台数を需要として扱い、その需要を満たすように車両流を構成しました。一方、`forward_traffic_ml` では、観測値を直接の車両生成命令にはせず、順方向シミュレーションのパラメータを補正するための信号として扱います。

## 2. 現在の位置づけ

このモデルはまだ作成途中です。公開版では、完成した交通シミュレータとしてではなく、順方向アプローチを検討するための設計と実装途中のコードを示しています。

そのため、実データを使った完全な再現実験や学習済み結果は含めていません。コードは、前処理、順方向シミュレーション、観測値との比較、補正ループへ接続するための試作として位置づけています。

## 3. 基本方針

順方向モデルでは、次の流れを基本にします。

```text
道路ネットワーク
  ↓
入口候補から車両発生
  ↓
道路リンク上を前進
  ↓
交差点で分岐
  ↓
観測点通過を集計
  ↓
観測交通量との差分を計算
  ↓
発生率・入口重み・分岐重みを補正
```

観測交通量は、特定の観測点から車両を直接生成するためには使いません。観測値を直接生成命令として使うと、見かけ上は観測値に合わせやすい一方で、実際の交通流として不自然な挙動になりやすいためです。

## 4. 補正対象

### 4.1 発生率

対象領域全体で、単位時間あたりにどれくらい車両を発生させるかを調整します。

### 4.2 入口重み

どの入口リンクから車両を発生させやすくするかを調整します。観測交通量が多い領域に車両が届きやすいよう、入口候補の重みを更新することを想定しています。

### 4.3 分岐重み

交差点でどの outgoing edge を選びやすくするかを調整します。観測点の通過台数が不足している方向へ、分岐選択が寄るようにすることを目指します。

### 4.4 OD傾向

将来的には、単純な入口・分岐重みだけでなく、車両がどの方向へ向かいやすいかを表すOD傾向も補正対象にする想定です。ただし、断面交通量だけからODを一意に決めることはできないため、追加の仮定や制約が必要になります。

## 5. 処理の流れ

### 5.1 前処理

前処理では、対象領域の道路ネットワークと観測点情報を読み込み、順方向シミュレーションで扱いやすい形式へ変換します。

公開版では、実観測地点の位置情報や実交通量を含む入力データは同梱していません。

### 5.2 シミュレーション

車両は入口候補から確率的に発生し、道路リンクの長さや速度制限に従って前進します。交差点では、接続先リンクの分岐重みに従って次のリンクを選択します。

### 5.3 観測点通過の集計

車両が観測点に対応する道路リンクを通過した場合、その観測点・時間窓ごとに通過台数を集計します。

### 5.4 観測値との比較

シミュレーションで得られた通過台数と観測交通量を比較します。比較指標としては、次のような値を想定しています。

- MAE
- RMSE
- Bias
- 相関係数
- 観測点ごとの誤差分布

### 5.5 補正ループ

比較結果をもとに、発生率、入口重み、分岐重みを更新します。最終的には、次のような反復ループを想定しています。

```text
simulate → compare → update parameters → simulate again
```

## 6. road_database_project との関係

`forward_traffic_ml` を進める中で、OSM Wayを直接使う構成では、交差点接続、描画形状、観測点対応、分岐重みの補正を同じデータ構造で扱うことが難しくなりました。

そのため、道路ネットワークを次のように分けて扱う必要が出てきました。

- 車両が移動するためのトポロジー
- 地図上に表示するためのジオメトリ
- 単方向の移動リンク
- 交差点での接続関係
- 観測点や分析単位との対応

この整理のために作成したのが `road_database_project` です。順方向モデルを安定して拡張するには、OSM Wayをそのまま使うのではなく、directed edge ベースの道路DBへ移行する必要があります。

## 7. ファイル構成

`forward_traffic_ml` には、順方向シミュレーション本体、補正実験、道路DB移行実験、可視化用データ生成、ビューア本体が含まれています。公開版では入力データと生成済みJSONを含めていないため、一部のスクリプトやビューアはそのままでは動きません。ただし、どの処理をどのファイルが担当しているかを追えるように、コード本体は残しています。

### 7.1 `src/`

| ファイル | 役割 | 公開版での注意 |
|---|---|---|
| `preprocess.py` | 実験用の小領域データを作成する前処理 | 実観測地点位置情報や交通量データは同梱していないため、入力データを別途用意する必要があります |
| `simulate_forward.py` | OSM Wayベースの最小順方向シミュレーション | `data/processed/` の前処理済みデータを入力にします |
| `compare_observed.py` | 観測値とシミュレーション通過台数を比較する | `results/` の生成済みCSVは公開版に含めていません |
| `branch_policy.py` | 交差点分岐確率 `theta` をsoftmaxで管理する | 分岐率補正実験の基礎部品です |
| `feedback_trainer.py` | 観測誤差を分岐確率更新へ戻す処理 | 実験途中の補正ロジックです |
| `run_training.py` | OSM Wayベースの分岐確率更新実験を実行する | 入力データ・結果出力先は公開版では空です |

| `road_db_network_loader.py` | 道路DBスナップショットを順方向シミュレーション用に読み込む | directed edgeベースへの移行実験で使います |
| `road_db_forward_simulator.py` | 道路DB directed edgeベースの順方向シミュレーション | 作成途中の道路DBベース実験です |
| `road_db_theta_policy.py` | 道路DB版の分岐スコア `theta` を管理する | directed edgeベースの分岐補正用です |

### 7.2 `viewer/`

`viewer/` は、上記の `export_*.py` で生成したJSONをブラウザで確認するための静的ビューア群です。

| ファイル | 役割 | 想定入力 |
|---|---|---|
| `index.html`, `app.js`, `style.css` | 順方向シミュレーションの診断ビューア | `viewer/data/diagnostics.json` |
| `observation_alignment.html`, `observation_alignment.js` | 観測点と道路DB geometry の対応確認 | `viewer/data/observation_alignment.json` |
| `road_variants.html`, `road_variants.js` | 道路フィルタ条件の違いを比較 | `viewer/data/road_variants.json` |
| `source_variants.html`, `source_variants.js` | 車両発生位置パターンの比較 | `viewer/data/source_variants.json` |
| `spawn_observation_points.html`, `spawn_observation_points.js` | 観測点と車両発生位置の対応確認 | `viewer/data/spawn_observation_points.json` |
| `conflict_volume_profiles.html`, `conflict_volume_profiles.js`, `conflict_volume_profiles.css` | 近接観測点ペアの交通量プロファイル確認 | `viewer/data/observation_alignment.json` などから派生した診断データ |

公開版では、これらの入力JSONを含めていません。理由は、観測点位置情報やそれに由来する派生データを含む可能性があるためです。そのため、ビューア本体は公開していますが、実データを表示するには、利用規約に従って入力データを取得し、対応する `src/export_*.py` を実行してJSONを生成する必要があります。

## 8. 公開版で除外しているデータ

公開版には、次のデータを含めていません。

- 実観測地点の緯度経度
- 断面交通量計測地点の詳細な位置情報
- 実交通量と位置情報を結合したJSON
- 前処理済みの道路ネットワークスナップショット
- シミュレーション結果JSON/CSV
- 学習・補正途中の生成データ

これは、断面交通量計測地点の位置情報およびそれに由来する派生データに再配布上の制限があるためです。

前処理では、観測地点を表す観測点コードと緯度・経度を対応付けるCSVを参照する設計になっています。この対応表では、観測点コードとその観測地点の緯度・経度を扱います。

この対応表は断面交通量計測地点の詳細な位置情報に該当するため、公開版には含めていません。また、この対応表を交通量CSV、道路ネットワーク、観測点マッチング結果と結合して生成したJSON/CSVも、位置情報に由来する派生データとして公開対象から除外しています。

公開版では、データそのものではなく、順方向アプローチの設計、コード構成、道路DBへ移行する必要性を示すことを目的としています。

## 9. 今後の展望

`forward_traffic_ml` は現時点では作成途中であり、分岐重みや車両発生位置の決め方にはまだ簡易的なルールが多く残っています。今後は、観測交通量と外部統計データを組み合わせ、より自然な順方向交通シミュレーションへ発展させることを目指します。

### 9.1 分岐重み `theta` の機械学習化

現在の `theta` 更新は、観測値とシミュレーション結果の差分をもとに、ルールベースで分岐重みを調整する考え方に近いものです。

今後は、交差点ごとの分岐選択を単純な手動ルールではなく、機械学習モデルによって推定する方向を検討します。たとえば、次のような特徴量を入力として、outgoing edge の選ばれやすさを推定することが考えられます。

- 道路種別
- 車線数
- 速度制限
- 観測点までの距離
- 周辺観測交通量
- 時間帯
- 上流・下流の接続構造
- 過去のシミュレーション誤差

この方向に進めることで、現在のルールベース更新よりも、道路構造や時間帯ごとの交通傾向を反映した分岐確率を学習できる可能性があります。

### 9.2 車両発生位置・発生量の推定

現状では、車両の発生位置は観測点の上流候補などをもとに簡易的に決めています。これは小規模な動作確認には有効ですが、都市全体の交通流を再現するには不十分です。

将来的には、OD統計や e-Stat などの官公庁データを活用し、どの地域からどの程度の交通需要が発生するかを推定するモデルを導入したいと考えています。

想定している方向性は次の通りです。

- 地域メッシュごとの人口・事業所・昼夜間人口などを使う
- OD統計や通勤・通学流動データを事前分布として使う
- 時間帯ごとの発生量を推定する
- 推定した発生需要を道路ネットワーク上の入口候補へ割り当てる
- 観測交通量との差分を使って、発生モデルと分岐モデルを同時に補正する

断面交通量だけからODを一意に決めることはできないため、外部統計データを事前情報として取り入れることが重要になります。これにより、観測点の近くで車を発生させるだけのモデルから、都市全体の交通需要をより自然に表すモデルへ拡張できると考えています。
